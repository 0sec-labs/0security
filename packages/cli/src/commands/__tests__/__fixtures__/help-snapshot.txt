### 0security
Usage: 0security [options] [command]

A security agent for your code: scan, fix, SBOM and evidence. Run 0security to open the console.

Options:
  -h, --help                       display help for command
  -p, --print <prompt>             Run one prompt headless: only the answer goes to stdout
  -c, --continue                   With -p: continue the most recent thread
  -r, --resume <id>                With -p: continue a saved thread

Work:
  scan [options] [target]          Scan a folder or git repository for security bugs; prints the
                                   findings as a report
  threat-model [options] [folder]  Draft the repository's threat model as a file for people to
                                   review (optionally as a pull request)
  probe [options] <url>            Send adversarial messages to a live model or agent endpoint and
                                   report the ones it obeys
  sbom                             Generate an SBOM from lockfiles, check one against known
                                   advisories, and scan model files
  findings [options]               Browse findings and change their status
  threads                          Start, follow and stop threads
  sentinels                        Create, run and change Sentinels

Setup:
  skills                           Skills and extensions: list, add
  models                           Models and provider connections
  computers                        Remote computers that run 0
  config                           Settings, API keys, team and setup checks (config doctor)

Run `0security <command>` to list its subcommands; `0security <command> <subcommand> --help` for flags.

Examples:
  0security -p "Review ./app for injection bugs"
  0security threads start "Map the login flow" --wait
  0security findings list --severity high --format json
  0security sentinels list --presets

### 0security findings burndown
Usage: 0security findings burndown [options]

Work through open findings in batches: one fix branch and pull request each, then a report

Options:
  --severity <levels>             Only these severities (critical, high, medium, low, info;
                                  comma-separated)
  --category <category>           Only this category
  --tool <name>                   Only findings reported by this tool
  --source <name>                 Alias of --tool
  --fingerprint <prefix>          Only findings whose fingerprint or id starts with this
  --limit <n>                     Attempt at most this many findings in this run; the next run
                                  continues with the rest
  --repo <dir>                    Git repository the findings are in (default: the current
                                  directory)
  --base <branch>                 Branch to start from and open pull requests against (default: the
                                  remote's default branch)
  --test <command>                Check to run after each change; repeat for several. A failing
                                  check makes the pull request a draft
  --ready                         Open pull requests ready for review even when no --test ran.
                                  Without it, a pull request with no checks is a draft
  --policy <file>                 Policy file (.json or .yaml) with fix rules and pull request
                                  conventions; any path you name. Default:
                                  ~/.0/fix-policy.json|yaml|yml
  --ticket <key>                  Ticket key such as SEC-123 for the {ticket} placeholder in your
                                  policy's pull request settings
  --no-pr                         Commit on the fix branches but do not push or open pull requests
  --concurrency <n>               Fixes at the same time, each in its own work tree (1 to 4)
                                  (default: "1")
  --budget <usd>                  Total spend for this run in USD; no new fix starts once it is used
                                  (default: "10")
  --per-fix <usd>                 Spend cap for one fix, in USD (default: "3")
  --max-consecutive-failures <n>  Stop after this many failed fixes in a row (default: "3")
  --max-failure-rate <fraction>   Stop when the share of failed fixes is above this (after
                                  --min-attempts) (default: "0.5")
  --min-attempts <n>              Fixes to attempt before the failure share can stop the run
                                  (default: "4")
  --model <model>                 Model for the fix threads (default: gpt-6-luna)
  --timeout <seconds>             Maximum seconds to wait for one fix (default: "1800")
  --retry                         Work again on findings that already have a fix branch or pull
                                  request
  --dry-run                       List what would be attempted and skipped; change nothing
  --history                       List the metrics row of each earlier run and exit
  --format <format>               Output: text or json (choices: "text", "json")
  --engine-url <url>              Attach directly to a running trusted engine
  --engine-token-env <name>       Environment variable holding the attached engine token
  --computer <id>                 Use a registered remote computer
  --computers-config <path>       Operator computer connection registry JSON file
  --db-path <path>                Control database of the local engine to attach to
  -h, --help                      display help for command

  --budget <usd>             Stop when the estimated spend reaches this many USD; partial findings
                             are kept (default: "5")
  --format <format>          Report format: json, md, sarif, html, pdf (default: "md")
  -o, --output <file>        Write the report to a file instead of stdout
  --fail-on <severity>       Exit 1 when a finding is at or above this severity (critical, high,
                             medium, low, info)
  --passes <n>               Scan this many times and merge the findings (a scan misses some issues
                             that another run finds); the budget is split between them, up to 5
                             (default: "1")
  --diff <ref>               Review only the files that differ from this git ref (for example
                             origin/main), and what they connect to; an empty diff scans nothing
  --prepass <mode>           auto runs the pattern scanners first when they are installed and gives
                             their hits to the scan as leads; off skips them (default: "auto")
  --scanner <id>             Scanner for the pre-pass (foxguard, semgrep, opengrep, gitleaks, trivy,
                             osv-scanner, checkov); repeat or separate with commas to use several
                             (default: foxguard). gitleaks, trivy and osv-scanner must be installed;
                             secret values are redacted
  --rules <file-or-folder>   Semgrep or OpenGrep rules for the pre-pass (a file or a folder); repeat
                             for several. Replaces the default rules and needs --scanner semgrep or
                             opengrep. Rules are never read from the scanned folder unless you name
                             them
  --context <file>           Give the scan this file (a threat model, notes on who may do what) as
                             lower-priority background; repeat for several. It can steer what the
                             scan weighs but cannot change how it works
  --policy <file-or-folder>  Check the code against these Markdown policies (a file or a folder of
                             .md files) and report pass or fail for each; repeat for several. Runs
                             the policy-check skill
  --org-policy <folder>      An organisation's policy folder: evaluated first, and wins when a
                             --policy says otherwise or uses the same id; repeat for several
  --scope <file>             Read the declared scope from the '## Scope' section of this Markdown
                             file (usually SECURITY.md). Findings that match a vector it lists as
                             out of scope are labelled, listed apart and left out of the counts,
                             --fail-on and the exit code; none are removed. In CI pass the base
                             branch's copy
  --repo-scope               Read SECURITY.md from the scanned folder as the declared scope. Off by
                             default: a change under review can edit that file; in CI pass the base
                             branch's copy with --scope instead
  --scope-sarif <mode>       With --scope: label (default) writes the scope as result properties;
                             suppress also marks out-of-scope results suppressed, which GitHub code
                             scanning then dismisses (default: "label")
  --repo-context             Also read .0/threat-model.md from the scanned folder as context. Off by
                             default: a change under review can edit that file; in CI pass the base
                             branch's copy with --context instead
  --repo-ignores             Also let the pre-pass scanners read their configuration and ignore
                             files from the scanned folder (.foxguard.yml, .semgrepignore,
                             .gitleaks.toml, .gitleaksignore, .trivyignore, osv-scanner.toml,
                             .checkov.yaml). Off by default: a change under review can use them to
                             hide findings. Inline suppressions such as nosemgrep always apply
  --skill <id>               Skill that holds the scan method (default: "scan")
  --model <model>            Model for the scan thread (default: gpt-6-luna)
  --batches <mode>           auto reviews a large folder in batches, one thread per group of entry
                             points, and records what each batch covered; on always does; off keeps
                             one thread (default: "auto")
  --batch-size <n>           Entry points one batch reviews (1 to 50); a folder with more than this
                             many is split under --batches auto (default: "8")
  --retries <n>              Run a batch again when it fails for a reason that may pass: a dropped
                             connection, a provider timeout, rate limit or server error (0 to 5; 0
                             turns it off). A thread that is not a batch is asked once to continue.
                             The cost of every attempt counts against --budget (default: "2")
  --coverage-rounds <n>      After a thread ends, send it a follow-up that names the source files it
                             never opened, up to this many times (0 to 5; 0 turns it off). Each
                             round counts against --budget (default: "1")
  --batch-timeout <seconds>  Longest one batch may run before it is cancelled and left pending (the
                             scan goes on with the next batch); --timeout still limits the whole
                             scan (default: "900")
  --concurrency <n>          Batches that run at the same time (1 to 3) (default: "1")
  --resume <scan>            Continue the units an earlier batched scan of this folder did not reach
                             (a scan id from its report, or latest); refuses when the git HEAD
                             changed unless --force
  --force                    With --resume: continue even though the folder's git HEAD changed
  --coverage [scan]          Print the coverage ledger of a batched scan of this folder (the latest,
                             or the id given) and exit; --format json for JSON
  --allow-partial            Exit by the findings alone (0, or 1 with --fail-on) when the scan stops
                             before it reviews everything; the report still says it is partial
  --plan                     List the entry points, the batches and a rough cost range for the
                             folder, then exit; calls no model and writes nothing
  --tiers <file>             An operator's tier map (YAML or JSON) that sets the budget, batches and
                             skill for this repository, or skips it. Default:
                             scan-tiers.yaml|yml|json in the 0 state folder. Never read from the
                             scanned folder on its own; in CI read it from the base branch
  --fail-on-skip             Exit 1 when the tier map skips this scan (default: exit 0, with the
                             skip stated in the report)
  --known <sarif>            SARIF from other tools: the scan is told what is already known and
                             looks for what they missed; findings are labelled new or already-known
                             (confirmedIndependently when the scan analysed it itself). Repeat for
                             several
  --only-new                 With --known: leave findings that match a known item out of the report
  --timeout <seconds>        Maximum seconds for the whole scan; what it reviewed so far is reported
                             as partial (default: "3600")
  --engine-url <url>         Attach directly to a running trusted engine
  --engine-token-env <name>  Environment variable holding the attached engine token
  --computer <id>            Use a registered remote computer
  --computers-config <path>  Operator computer connection registry JSON file
  --db-path <path>           Control database of the local engine to attach to
  -h, --help                 display help for command
